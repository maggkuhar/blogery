# Уроки — Внешний трафик

*Специфические правила, договорённости, причуды этого проекта.*

## Правила

### Один блок = один blueprint = одна папка

**Правило:** любой новый блок — новый Flask blueprint в отдельной одноимённой папке. `app.py` остаётся ТОЛЬКО точкой входа: создание Flask, `register_blueprints`, ничего больше. Не вносить роуты в `app.py`.

**Why:** базовое архитектурное решение проекта. Иначе при росте `app.py` превратится в свалку, мёрджи поломают всё. Сейчас уже 8+ блоков работают по этому шаблону.

**How to apply:** если пользователь просит «добавь страницу X» — сначала решаю в какой блок (существующий или новый), создаю файлы по шаблону соседних блоков, регистрирую blueprint в `app.py`.


### Общий код — только в `database.py` и `constants.py`

**Правило:** утилиты для БД (`get_db`, `init_db`) — только в `database.py`. Перечисления (PLATFORMS, STATUSES, типы) — только в `constants.py`. Шеред-шаблоны — `templates/_nav.html`, `templates/form.html`.

**Why:** не плодить дубли. Если в blueprint появляется хелпер для БД — это знак вынести в `database.py`.

**How to apply:** перед добавлением новой функции работы с БД проверяю — может, она уже в `database.py` или должна туда переехать.


### Боты для Instagram/TikTok — только на отдельных аккаунтах

**Правило:** при подключении бота к Instagram или TikTok использовать аккаунт, созданный специально для бота. Никогда не использовать основной (пользовательский) аккаунт.

**Why:** соцсети регулярно банят бот-активность. Бан основного аккаунта = потеря живой аудитории и контента. Бан бот-аккаунта = заводим новый, ничего не теряем.

**How to apply:** если пользователь говорит «подключи мой инстаграм» — уточняю «бот-аккаунт?» и предлагаю создать отдельный, если ещё нет.


### Авто-поиск — официальные API где есть, парсинг где нет

**Правило:** для VK и YouTube — только официальные API (VK API / Google API). Для Instagram и TikTok — бот-аккаунт как обычный пользователь (нет нормальных API).

**Why:** API — стабильно и без бана. Парсинг — компромисс там где API закрыт.


### Архитектура «разведчик + контакт»

**Правило:** боты в проекте делятся на две роли — Scout (только сбор данных, почти не палится) и Contact (действия — лайки, комменты, сообщения, по лимитам). Каждый бот = один аккаунт = одна соцсеть. Без ограничения количества.

**Why:** разделение нагрузки и риска. Скаут собирает базу — его сложно поймать. Контакт работает по людям — рискует баном, но риск изолирован.

**How to apply:** при создании нового бота — сразу определяю роль и настройки (лимиты, задержки) под неё.


### Индивидуальные настройки и история банов

**Правило:** каждый бот в панели имеет: лимиты в день, задержки между действиями, расписание, статус (активен/заблокирован/прогрев), историю банов с причинами.

**Why:** при бане надо знать причину чтобы новый бот не попал так же. История банов — отдельное поле, не удалять.

**How to apply:** при бане — фиксирую причину перед созданием нового бота. Не «удалить и забыть».


### Порядок разработки — каркас → автопоиск → AI

**Правило:** новый блок начинаем с базы (БД + веб-таблица + ручное добавление). Только после этого подключаем автопоиск (API/парсинг). AI-анализ и шаблоны — последним этапом.

**Why:** без каркаса автопоиск некуда складывать. Без данных AI-анализу нечего анализировать. Скип каркаса = переделка всего потом.


## Причуды кода

### `database.py` использует один общий `blogery.db`

Все блоки пишут в одну SQLite. Не выносить таблицы блоков в отдельные базы — внутренняя интеграция (например, шаблоны ссылаются на блогеров) работает через JOIN.


### Шеред-форма `templates/form.html` для трёх сущностей

Один шаблон используется для блогеров, групп и каналов — структура карточек схожая. Если для одной сущности нужно отдельное поле — добавлять условный блок в `form.html`, не дублировать шаблон.
